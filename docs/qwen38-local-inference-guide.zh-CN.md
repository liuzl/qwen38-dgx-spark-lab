# Qwen3.8-27B 本地推理怎么选：量化、Runtime、投机解码与 Agent 正确率

> 数据截止：2026-08-27。Runtime、模型转换和内核仍在快速更新；本文中的精确
> 数字用于说明方法与决策边界，不代表未来版本的固定排名。

本地部署大模型时，最容易回答的问题是“每秒能生成多少 token”，最容易答错的
问题却是“哪套方案最适合真实工作”。量化格式、推理 Runtime、投机解码、上下文、
并发和工具调用共同决定最终体验。只挑其中一个数字，往往会得到错误的结论。

本文用 Qwen3.8-27B 的多组受控实验说明一套可复用的评测和选型方法。具体数字属于
特定硬件与软件版本，方法和决策边界才是重点。

## 结论先行

1. **更低位量化首先解决容量问题，不保证更快。** 模型文件更小，不代表 Metal、
   CUDA 或特定算子对该量化格式的执行效率更高。
2. **Runtime、模型产物和加速方式应视为完整部署栈。** 不同 Runtime 使用不同转换
   产物时，比较的是整套方案，不是纯 Runtime 性能。
3. **投机解码不是固定倍增器。** 收益会随任务、上下文、并发、量化和硬件变化，
   最佳 depth 必须在目标工作负载上实测。
4. **单流、并发和长上下文是三个不同问题。** 单流最快的方案，可能在并发或长上下文
   下迅速失去优势。
5. **Agent 服务应先看任务完成率，再看 tok/s。** 工具名、参数和多轮闭环失败时，
   更高吞吐没有业务价值。

## 一、先定义你真正要优化的目标

“本地推理快不快”至少包含四类互不等价的目标：

| 目标 | 主要指标 | 常见误判 |
|---|---|---|
| 单人交互 | TTFT、单流 decode、端到端时间 | 只看模型加载后的峰值 tok/s |
| 多请求服务 | aggregate throughput、p95、排队长度 | 用单流结果推测并发能力 |
| 长文与代码库 | prefill、长上下文 decode、内存余量 | 只设置大窗口，却不发送长输入 |
| Agent 与工具调用 | 任务完成率、工具名、参数、闭环结果 | 工具 JSON 能解析就算成功 |

这四类目标需要分别测试。把它们压成一个“综合速度”数字，会掩盖真正的瓶颈。

## 二、相同客户端协议下，硬件和完整栈的差距会被工作负载放大

我们让同一套客户端 prompt、temperature、输出长度、并发和唯一请求前缀分别请求
DGX Spark 与 M3 Max 上已完成资格验证的 4-bit 栈：

| Case | 指标 | DGX Spark vLLM + DFlash2 | M3 Max 原生 MLX 栈 |
|---|---|---:|---:|
| PP1080/TG256 C1 | decode tok/s | 60.38 | 44.24 |
| PP1080/TG256 C4 | aggregate tok/s | 143.70 | 18.19 |
| PP16345/TG256 C1 | decode tok/s | 69.83 | 14.65 |

短单流中，Apple Silicon 已达到参考服务相当一部分性能；到了并发和持续长上下文，
差距显著扩大。这不是“Mac 能不能运行 27B”的问题，而是内存带宽、批处理实现、
KV 管理和投机解码在不同形状下共同作用的结果。

因此，跨硬件比较至少要包含 C1、一个真实并发档和一个目标长度的长上下文档。
完整协议和原始聚合结果见
[DGX Spark 与 M3 Max 对比](cross-platform-comparison.md)。

## 三、2-bit 值得测试，但不要把“更小”误写成“更快”

另一条实验使用约 10.6 GB 的社区 IQ2_M GGUF，在 M3 Max 上通过 llama.cpp Metal
运行。该 checkpoint 与上面的 4-bit 主线并不相同，因此这组数据用于回答“紧凑
GGUF 路线是否有价值”，不能作为纯量化质量对照。

在固定的 PP1K/TG256 单流协议下：

| 模式 | decode tok/s | 相对 AR |
|---|---:|---:|
| AR | 11.71 | - |
| MTP depth 1 | 16.23 | +38.5% |
| MTP depth 2 | 18.28 | +56.1% |
| MTP depth 3 | 19.90 | +69.9% |

本组实验的 checkpoint、Runtime revision、正确性门和排除项见
[Apple Silicon 2-bit 实验记录](apple-silicon.md#experimental-2-bit-gguf-track)与
[结构化汇总](../benchmarks/results/apple-m3-max-llamacpp-iq2-summary-2026-08-26.json)。

结果说明两件事：

- 内置 MTP 可以显著改善低位 GGUF 的单流生成；
- 即使启用 MTP，这条 2-bit 路线仍明显慢于同机的原生 4-bit MLX 栈。

2-bit 的核心价值是较小的模型体积、跨平台 GGUF 生态和资源受限时的可运行性。
如果机器有足够内存，不能仅凭位数更低就把它设为日常默认。

四组温度为零的代码、中文算术、多语言和结构化输出 canary 在 MTP depth 1 至 3
都与 AR 逐字一致。这证明了这些样本中的运行一致性，但不证明模型在推理、编码和
长 Agent 任务上的总体质量不受量化影响。

## 四、投机解码必须按任务和形状测量

投机解码通过先生成候选 token、再由目标模型验证来换取速度。接受率高时收益明显；
接受率下降时，草稿计算和验证可能成为额外开销。

同一配置在短代码单流上可能接近满接受，到了长上下文或并发时却明显下降。社区的
Apple Silicon 对比也显示，M4 Max 与 M5 Max 的最佳 MTP depth 并不相同，继续增加
depth 会从正收益转为负收益
（[外部对比图](https://x.com/StefanoGogioso/status/2092557016308850840)）。

所以报告投机解码结果时，至少同时给出：

- AR 基线与加速后的 decode tok/s；
- draft token 数和 accepted token 数；
- prompt 类型、输入长度与输出长度；
- 并发数和每个请求的延迟；
- temperature、seed 和采样方式；
- 加速开关前后的输出一致性或任务正确率。

只写“开启 MTP 后翻倍”，无法判断这个结论能否迁移到其他任务。

## 五、Agent 时代，最快的 Runtime 不一定最好

一组公开的 DGX Spark 完整栈横评报告：Coding 场景中 SGLang 吞吐领先 vLLM；到了
18 个 Agent Tool Calling 样本，SGLang 完成 16 个，vLLM 完成 18 个。由于两者使用
的 NVFP4 转换产物不同，llama.cpp 又使用 GGUF Q4_K_M，这不是纯 Runtime A/B；
18 个样本也不足以形成普遍排名。但它清楚展示了正确的决策顺序：

> 先通过 Agent 正确性门，再在通过者中比较性能。

该报告及其限制见
[MinLiBuilds 的总结](https://x.com/MinLiBuilds/status/2092413796455444821)。

一个有用的工具评测集不应只检查响应里是否出现 `tool_calls`，还应验证：

1. 是否选择了正确工具；
2. 参数是否满足 schema；
3. 参数值是否解决当前任务；
4. 工具结果返回后能否继续推理；
5. 多轮调用是否按正确顺序执行；
6. 最终答案是否真正完成任务。

生产切换还应增加足够样本、重复运行、错误分类和持续时间测试。一次强制工具调用
smoke 只能证明 API 路径接通，不能证明 Agent 已经可用。

## 六、五种常见的无效 Benchmark

### 1. Prompt 与输出装不进每个 slot 的 context

服务的总 context 可能被多个并发 slot 平分。如果 prompt 已经接近单 slot 上限，
模型仍可能返回 HTTP 200，却在达到目标输出长度之前停止。必须检查实际 prompt 和
completion token 数，不能只看请求成功。

### 2. Prompt cache 污染 TTFT

重复使用完全相同的 prompt 可能让后一次请求直接命中缓存。缓存命中是有价值的产品
能力，但不能冒充冷 prefill 性能。Benchmark 应使用唯一请求前缀，并把缓存实验单列。

### 3. 相同模型名掩盖不同权重产物

NVFP4、GGUF、MLX 和不同社区转换可能修改 tensor 类型、校准方式甚至模型内容。
当文件不同，结论应写成“完整部署栈比较”，而不是“Runtime A 比 Runtime B 快”。

### 4. 只看 `model loaded`

模型成功加载不代表首个真实请求、长上下文、工具模板或并发路径可用。最小资格验证
必须包含真实 API 请求和目标形状。

### 5. 只报速度，不报失败与输出边界

完整报告应同时包含 finish reason、失败数、实际 token 数、TTFT、端到端延迟、
decode、aggregate throughput，以及投机解码的接受情况。

## 七、一套可复用的资格验证流程

### 阶段 1：固定实验对象

- 固定模型文件 revision 与 hash；
- 固定 Runtime commit、驱动和关键依赖；
- 记录量化格式、KV 类型、context、batch 和并发；
- 隔离生产服务与实验服务。

### 阶段 2：正确性先行

- 温度为零的文本和结构化 canary；
- AR 与投机解码输出比较；
- API、模板、工具 schema 和多轮闭环测试；
- 检查实际 completion token 数和 finish reason。

### 阶段 3：分形状测性能

- 短上下文 C1；
- 目标并发档；
- 目标长度的长上下文；
- 冷 prefill 与缓存命中分别报告；
- 对 workload-sensitive 参数做小范围 sweep。

### 阶段 4：用真实任务做最终门禁

- Agent 或领域任务应有独立正确答案；
- 样本数量足以暴露低频 parser 和工具错误；
- 报告任务成功率、错误类型和性能；
- 只有正确率不退化时，性能提升才可进入生产候选。

## 八、如何做部署选择

- **个人单流使用：** 从平台原生优化、质量足够的 4-bit 路线开始，再按内存调整。
- **资源受限或需要跨平台：** 测试 2-bit/3-bit GGUF，但单独验证质量和长任务。
- **多人并发服务：** 优先连续批处理、KV 管理和 p95，不用单流峰值代替容量测试。
- **Agent 服务：** 正确率是硬门，吞吐只用于通过门禁后的排序。
- **需要投机解码：** 针对真实 prompt、上下文和并发选择 depth，不复制别人的最优值。

最终要选的不是“最快模型文件”或“最热门 Runtime”，而是在目标硬件、目标任务和目标
并发下，能够稳定完成工作的完整部署栈。

## 结语

本地大模型评测正在从“能不能加载”和“每秒多少 token”，走向“能不能持续、正确地
完成真实任务”。Qwen3.8-27B 的这些实验给出的最重要结论并不是某个固定速度或最佳
参数，而是一条简单原则：

> 先证明输出和任务正确，再证明性能；先测真实形状，再讨论部署选择。

仓库中的[平台中立 Benchmark](../scripts/benchmark-openai.py)、
[Apple Silicon 实验](apple-silicon.md)和
[Spark Benchmark 方法](benchmarks.md)提供了复现这些步骤的代码与聚合结果。
