# NVIDIA A100 qualification track

For the concise decision record covering the full experiment and native
uncensored-LoRA port, see the
[Qwen3.8-27B A100 porting report](a100-porting-report.md).

This track ports the Qwen3.8-27B text-serving workload to one NVIDIA A100 and
keeps its measurements separate from the DGX Spark and Apple Silicon results.
The shared OpenAI benchmark protocol makes the complete stacks comparable; it
does **not** turn different checkpoints, precisions, or speculative decoders
into a pure hardware comparison.

The pinned FP8 checkpoint metadata was also inspected locally before the weight
download completed. It declares `quant_method=fp8`, E4M3 data, dynamic
activation scaling, `128 x 128` weight blocks, one MTP hidden layer with shared
embeddings, and 882 excluded module entries. Those exclusions include the
vision tower, embeddings, normalization/state components, and `lm_head`, so
the artifact is mixed precision rather than uniformly eight-bit.

The Docker client is newer than the daemon and must use
`DOCKER_API_VERSION=1.43` on this node. This is an environment compatibility
setting, not a Qwen or CUDA optimization.

The first image is vLLM 0.28.0's x86-64 CUDA 12.9 build, pinned by manifest
digest in the example configuration. The generic `latest` image currently uses
CUDA 13.0; it is intentionally excluded from the first run because the node's
R550 driver would add a separate forward-compatibility variable. CUDA 12.x
minor-version compatibility supports Linux drivers from 525.60.13 onward. A
local one-shot container probe confirmed that this pinned image imports vLLM,
PyTorch and Transformers, initializes CUDA, and sees the A100 as `sm_80`.

## Evidence boundaries

- **Locally observed:** the environment table and results added under
  `benchmarks/results/` after a completed run.
- **Upstream claim:** the official Qwen checkpoint is compatible with vLLM;
  current vLLM recipes require vLLM 0.17.0 or newer and Transformers 5.8.0 or
  newer for this model family. See the
  [official model card](https://huggingface.co/Qwen/Qwen3.8-27B) and
  [vLLM recipe](https://recipes.vllm.ai/Qwen/Qwen3.8-27B).
- **Working hypothesis:** the official FP8 checkpoint should select vLLM's
  weight-only W8A16/Marlin path on Ampere and leave materially more KV/cache
  headroom than BF16. Kernel selection, successful loading, quality gates, and
  measured free memory are required before this becomes a result.
- **Not assumed:** that the DGX Spark NVFP4 checkpoint or its Blackwell kernels
  work on A100; that A100 FP8 behavior matches Hopper/Blackwell; or that a model
  which loads has passed tool-use and quality gates.

## Minimum viable port

The first qualified arm is deliberately simple:

1. Official `Qwen/Qwen3.8-27B-FP8` checkpoint at a full pinned revision.
2. Official vLLM image pinned by digest after pull.
3. One GPU, autoregressive decoding, 32K maximum context, unquantized KV cache.
4. Loopback-only OpenAI-compatible endpoint with no production routing.
5. Eager execution for the first load because CUDA-graph startup hangs have
   been reported on Ampere with this checkpoint.
6. No LoRA, DFlash2, MTP, FP8 KV cache, or online quantization until the
   checkpoint baseline passes.

`LANGUAGE_MODEL_ONLY=1` is intentional for this text-serving comparison. It
does not qualify the vision path, but avoids reserving memory for a capability
outside the workload. Set it to `0` and run separate multimodal correctness and
resource gates before claiming vision support.

## A100-specific serving choices

### Weights and kernels

A100 is Ampere (`sm_80`). It has BF16/FP16 and INT8 Tensor Cores but no native
FP8 Tensor Core execution. Current vLLM loads FP8 checkpoints on Ampere as
weight-only W8A16 and should select `MarlinFP8ScaledMMLinearKernel`. The startup
log is the gate: a PyTorch/emulation or dequantization fallback is a different
arm and must not inherit the Marlin result label.

Use backend auto-selection for the first run, then record its choices. For the
full-attention layers, vLLM's Ampere priority selects FlashAttention, normally
FA2. Do not force a Blackwell backend or copy Spark `sm_121` flags to A100.

### Eager first, graphs second

An upstream vLLM 0.27.1 report reproduces a Qwen3.8-27B-FP8 startup hang during
CUDA Graph/`torch.compile` capture on Ampere; `--enforce-eager` reached serving
state. The first A100 arm therefore uses eager execution. vLLM 0.28.0 graph mode
is tested only as a bounded A/B with a startup timeout, identical KV capacity,
and automatic rollback to eager.

### KV cache and context

Keep `KV_CACHE_DTYPE=auto` for the first run. On Ampere, FA2 supports BF16/FP16
KV but not FP8 KV; selecting FP8 KV can change the attention backend as well as
the cache precision, so it is not a one-variable memory comparison. Test FP8 KV
later as a separately labeled stack and rerun long-context canaries.

Start at 32K even though the checkpoint supports 262K natively. After vLLM
profiles the model, record `Available KV cache memory` and maximum concurrency.
For controlled eager/graph or scheduler A/B runs, set `KV_CACHE_BYTES` to the
same conservative value; this is more reproducible than allowing each arm's
profiling result to silently change its KV pool.

CPU offload is not part of the default path. It transfers weights over PCIe on
each forward pass and changes the serving regime; use it only as an explicitly
labeled capacity fallback.

### Scheduler and prefix cache

Chunked prefill stays enabled. vLLM prioritizes decode tokens and uses the
remaining `MAX_NUM_BATCHED_TOKENS` budget for prompt chunks. Sweep `4096`,
`8192`, then `16384`: smaller budgets tend to protect ITL, while larger budgets
improve TTFT/prefill throughput. Do not infer the optimum from model size.

Start with `MAX_NUM_SEQS=8`, matching the first concurrency ceiling, then test
`4/8/16` only if queueing or GPU utilization shows a useful boundary. Raising
it without concurrent workload evidence only increases graph/profile shapes
and memory pressure.

Prefix caching on hybrid GDN/full-attention models uses evolving hybrid-cache
logic and requires chunked prefill in the default aligned Mamba-cache mode.
Validate both a unique-prefix miss and an identical-prefix hit. With MTP,
re-measure prefix reuse separately: an open upstream issue reports a 1,648-token
recompute boundary and a 30-40% batch-throughput loss for one Qwen3.8 layout.

### Speculative decoding

Autoregressive decoding is the binding baseline. Then test the in-checkpoint
MTP head at depths `1`, `2`, and `3`, using the same greedy canaries and C1/C4
workloads. Read accepted and drafted token counters from `/metrics`; higher
tok/s without active/healthy acceptance is not an MTP result.

DFlash2 is lower priority on A100. An upstream Ampere report shows that trying
to quantize its BF16 draft through the generic FP8/Marlin path can fail on
non-tile linears. It also adds roughly another draft checkpoint's memory and
changes prefix-cache behavior. Test it only after native MTP has a measured
decision boundary.

### Correctness and generation modes

Keep two protocols separate:

- **Deterministic runtime qualification:** thinking off, temperature `0`, fixed
  seed, fixed token counts. This is for exact canaries, runtime A/B, TTFT, ITL,
  and throughput. The launch template defaults thinking off so Chat,
  Responses, and Messages API smoke tests share the same mode.
- **Model-quality qualification:** use Qwen's recommended sampling settings.
  Thinking mode uses temperature `1.0`, top-p `0.95`, and top-k `20`;
  non-thinking mode uses temperature `0.7`, top-p `0.8`, top-k `20`, and
  presence penalty `1.5`. These stochastic results are quality checks, not
  latency comparisons against the deterministic protocol.

For Agent qualification, a parseable tool call is only the first gate. Check
the exact tool name and argument schema, feed a tool result back, and require a
correct final answer. Run both thinking-off and the intended production
`reasoning_effort`; Qwen warns that lower effort can reduce per-turn latency
while increasing retries and total task cost.

### Production boundary after qualification

The first service binds to loopback and is not a deployment. Before exposing
it to another host, add authentication and an explicit request queue limit.
Use `max_num_queued_reqs` as a coarse overload valve and derive any queued-token
limit from measured prefill throughput and the TTFT service target. Record
request failures, queue time, KV-cache usage, prefix hit rate, and speculative
accepted/drafted tokens from `/metrics`; do not infer health from GPU
utilization alone.

Copy `configs/qwen38-a100.env.example` to a private `.env`, resolve its image
digest and model revision, source it, and launch with:

```bash
export DOCKER_API_VERSION=1.43  # only where the old daemon requires it
scripts/serve-a100.sh
```

Do not commit the populated environment file, model/cache locations, tokens,
hostnames, addresses, or raw generations.

## Success gates

The A100 arm is qualified only when all of these are true:

1. **Load:** container health succeeds at the pinned model and image revisions;
   the log confirms the intended FP8 W8A16/Marlin selection and contains no
   silent CPU offload or dequantization fallback.
2. **API and tools:** Chat Completions, Responses, Anthropic Messages, exact text
   replies, and a forced tool name/schema pass with `scripts/validate-apis.py`.
3. **Correctness:** deterministic code, Chinese arithmetic, multilingual, and
   structured-output canaries are complete and satisfy their task constraints.
   Raw text remains under ignored `benchmarks/raw/`; only hashes and aggregate
   pass/fail results may be published.
4. **Benchmark validity:** every measured request succeeds, returns the requested
   completion length, reports usage, and has zero unintended prefix-cache hits.
5. **Performance:** record TTFT, decode rate/ITL, end-to-end latency, aggregate
   throughput, and C1/C4 concurrency with the shared client-owned workload.
6. **Resources:** record peak GPU memory, utilization, temperature, and power for
   each measured arm, plus post-load memory headroom.
7. **Stability:** a bounded repeated-request smoke test completes with no request
   failures, container restarts, health failures, or growth that ends in OOM.

No throughput number is promoted if the corresponding correctness or validity
gate fails.

## Qualified default

For the exact pinned model, image, driver, and A100 in this run, the recommended
text-serving configuration is FP8 W8A16/Marlin, native MTP depth 3, vLLM's
default `FULL_AND_PIECEWISE` CUDA Graph mode, BF16 KV cache, 8192 batched tokens,
8 maximum active sequences, and a 32K admission limit. Keep eager AR as the
rollback path. This is a revision-bound result, not a universal Ampere preset.

### Capacity-oriented deployment profile

The throughput figures in this document remain bound to the 32K, 8-sequence,
8192-batched-token benchmark profile above. A later deployment qualification
traded excess KV allocation for a larger admission limit and more short-request
concurrency:

| Setting | Deployed value |
|---|---:|
| Maximum model length | 131,072 |
| Fixed BF16 KV cache | 24 GiB |
| Maximum active sequences | 32 |
| Maximum batched tokens | 16,384 |

The fixed KV pool contained 338,297 tokens: 2.58 full 128K requests, about 41
8K requests by KV capacity, and a scheduler cap of 32 active sequences. Both
model aliases passed 64/64 requests at C32, and one request with 124,021 prompt
tokens completed successfully. After the ordinary C32 gates, about 18.5 GiB
remained free including the pre-existing co-resident processes; exercising the
124K shape left about 15.1 GiB free.

This is a capacity and correctness qualification, not a new throughput
benchmark. The official checkpoint includes a roughly 0.86 GiB vision tower,
but this service still uses `LANGUAGE_MODEL_ONLY=1`. Remove that flag only in a
separate multimodal arm, limit image/video inputs, and rerun image, video,
tool-use, memory, concurrency, and long-context gates before claiming
multimodal support.

## Controlled tuning order

Hold the prompt corpus, checkpoint revision, image digest, context limit, output
length, temperature, and seeds fixed. Change one decision variable at a time:

1. Establish the official FP8 autoregressive C1/C4/long-context baseline in
   eager mode.
2. Sweep only batching limits that affect the target workload; retain C1 TTFT as
   a guardrail while optimizing C4 aggregate throughput.
3. Compare CUDA Graph against eager only after the graph arm starts reliably.
4. Test the model's built-in MTP at small depths only after exact canaries pass.
5. Run a bounded official BF16 arm as a quality and quantization reference, not
   as the default deployment candidate.

| Arm | Change from qualified FP8 eager AR | Decision it answers |
|---|---|---|
| A0 | None | Binding correctness and performance baseline |
| A1 | Batch tokens 4096 / 16384 | ITL guardrail versus TTFT/throughput |
| A2 | `MAX_NUM_SEQS` 4 / 16 | Useful concurrency ceiling |
| A3 | CUDA Graph with a bounded startup | Whether graph capture is reliable and faster |
| A4 | FP8 KV, recording changed attention backend | Capacity benefit versus quality and latency |
| A5 | Native MTP depth 1 / 2 / 3 | Acceptance-adjusted single-stream benefit |
| A6 | BF16 weights, abbreviated | Quantization quality reference |

A1 and A2 need not be a Cartesian product: select the better A1 setting, then
test sequence limits. Skip A3-A5 as soon as correctness fails or the candidate
is dominated on the target workload.

## First A100 result: FP8 eager autoregressive

The first run completed on 2026-09-04 with the official pinned FP8 checkpoint
and vLLM 0.28.0 CUDA 12.9 image. The intended path was confirmed: W8A16 Marlin,
FlashAttention 2 for full attention, and Triton for GDN decode. Loading used
28.02GiB; vLLM allocated 41.64GiB of BF16 KV cache, or 593,920 tokens.

| Case | TTFT | Decode | ITL | Aggregate output |
|---|---:|---:|---:|---:|
| PP1K/TG256 C1 | 0.529s | 11.90 tok/s | 84.04ms | 11.66 tok/s |
| PP1K/TG256 C4 | 1.747s mean | 10.98 tok/s mean | 91.11ms mean | 40.99 tok/s |
| PP16K/TG256 C1 | 6.703s | 11.56 tok/s | 86.47ms | 8.90 tok/s |

All 10 benchmark requests returned 256 tokens with zero failures and zero cache
hits. The 64-request C4 stability smoke also passed with zero failures, zero
container restarts, and no OOM. However, only three of four deterministic
quality canaries passed: the Chinese arithmetic case hit the 256-token limit
without reaching the expected answer. This run is therefore `partial`; its
throughput is diagnostic and is not promoted as a qualified platform result.

The result shows the expected A100 tradeoff: the official FP8 artifact fits
comfortably as weights and leaves a large KV pool, but weight-only FP8 Marlin
plus eager autoregressive decoding is slow. MTP and a bounded CUDA Graph arm are
the next decision-changing tests. See the
[sanitized result](../benchmarks/results/a100-80gb-vllm-fp8-eager-ar-2026-09-04.json),
[OpenAI benchmark artifact](../benchmarks/results/a100-80gb-vllm-fp8-eager-ar-openai-2026-09-04.json),
and [canary summary](../benchmarks/results/a100-80gb-vllm-fp8-eager-ar-canaries-2026-09-04.json).

Against the existing Spark NVFP4 + DFlash2 K7 stack under the same client-owned
prompt shapes, A100 eager AR decode was 80.29% lower at short C1 and 83.44%
lower at 16K C1; C4 aggregate throughput was 71.48% lower. Short-prompt TTFT was
similar. This is a complete-stack comparison, not a pure A100-versus-GB10
hardware result. The structured comparison is in
[DGX Spark versus A100](../benchmarks/results/dgx-spark-vs-a100-fp8-2026-09-04.json).

### MTP and CUDA Graph result

The controlled MTP sweep established that the slow first result was a software
path, not an A100 hardware limit:

| Arm | MTP acceptance | PP1K C1 decode | PP1K C4 aggregate | PP16K C1 decode |
|---|---:|---:|---:|---:|
| Eager AR | — | 11.90 | 40.99 | 11.56 |
| Eager MTP K1 | 97.85% | 20.84 | 71.98 | 19.62 |
| Eager MTP K2 | 95.05% | 28.98 | 96.15 | 29.25 |
| Eager MTP K3 | 92.63% | 33.10 | 111.06 | 36.25 |
| CUDA Graph MTP K3 | 92.37% | **124.48** | **251.67** | **91.05** |

vLLM 0.28.0 successfully compiled and captured `FULL_AND_PIECEWISE` CUDA
graphs on this A100, despite the earlier upstream v0.27.1 Ampere hang report.
Compilation added 79.8 seconds to startup and reduced the KV pool from 40.95 to
39.21GiB, but it changed the serving decision: graph K3 is 3.76x eager K3 for
short C1 decode and 2.27x for C4 aggregate throughput.

Under the shared client protocol, graph K3 beats the existing Spark reference
on decode and concurrency: +106% short C1 decode, +75% C4 aggregate, and +30%
16K decode. It does **not** yet beat Spark on long-prompt end-to-end latency:
16K TTFT is 6.38 seconds versus 1.82 seconds, so the 256-token aggregate rate
remains lower. The next useful experiment is a larger chunked-prefill token
budget, not deeper MTP. See the
[MTP sweep result](../benchmarks/results/a100-80gb-vllm-fp8-mtp-sweep-2026-09-04.json)
and [Spark comparison](../benchmarks/results/dgx-spark-vs-a100-fp8-graph-mtp-k3-2026-09-04.json).

Raising `max_num_batched_tokens` from 8192 to 16384 did not improve 16K C1
TTFT or decode. It reduced C4 TTFT from 1.70 to 1.45 seconds but slightly reduced
C4 decode, leaving aggregate throughput effectively unchanged. Keep 8192 as the
balanced default; do not continue this sweep for the current workload. The
[controlled comparison](../benchmarks/results/a100-fp8-graph-mtp-k3-bt8k-vs-bt16k-2026-09-04.json)
preserves the full metrics.

### BF16 versus FP8 on A100

A final same-protocol graph K3 comparison found complementary strengths:

| Case | FP8 | BF16 | Binding result |
|---|---:|---:|---|
| PP1K C1 decode | **124.48** | 83.93 | FP8 +48% |
| PP1K C1 TTFT | 0.437s | **0.354s** | BF16 -19% |
| PP1K C4 aggregate | **251.67** | 230.39 | FP8 +9% |
| PP1K C4 TTFT | 1.703s | **1.078s** | BF16 -37% |
| PP16K C1 decode | **91.05** | 65.85 | FP8 +38% |
| PP16K C1 TTFT | 6.375s | **4.559s** | BF16 -28% |
| PP16K C1 end-to-end | 9.176s | **8.431s** | BF16 -8% |

FP8 is the default for interactive decode, concurrency, and memory capacity.
BF16 is a valid alternative for long-input/short-output workloads where prefill
dominates. BF16 loaded 51.02GiB and left 16.64GiB of KV cache (187,245 tokens,
5.71 concurrent 32K requests), versus FP8 graph K3's 39.21GiB KV pool (441,782
tokens, 13.48 concurrent 32K requests). All four 512-token deterministic
canaries matched FP8 and BF16 byte-for-byte. See the
[performance comparison](../benchmarks/results/a100-fp8-vs-bf16-graph-mtp-k3-2026-09-04.json)
and [canary comparison](../benchmarks/results/a100-fp8-vs-bf16-graph-mtp-k3-canaries-2026-09-04.json).
The private raw artifacts remain on the test node; their filenames, sizes, and
SHA-256 digests are recorded without paths in the
[raw-log index](../benchmarks/results/a100-log-index-2026-09-04.json).

Stop a sweep when a candidate fails correctness, OOMs, or is dominated on both
latency and throughput by an already qualified arm. DFlash2 remains a later,
separate experiment because attaching a drafter changes both memory and output
acceptance behavior.

## X experience scan

An X search on 2026-09-03 found no reproducible result for the exact stack of
one A100 80GB, official Qwen3.8-27B-FP8, and vLLM. The following posts are
directional evidence only and their throughput is excluded from the local A100
comparison:

- A two-RTX-3090 Qwen3.8-27B AWQ/TP2 report claimed 576/576 successful requests
  at HTTP concurrency 192, but recommended active GPU concurrency 8 and reported
  about 251 aggregate tok/s at C8. Different checkpoint, GPU count, and protocol:
  useful only for retaining `MAX_NUM_SEQS=8` as an early candidate.
  [Post](https://x.com/mochi_mochi_lab/status/2094924393671709061)
- A DGX Spark NVFP4 report claimed MTP depth 2 changed decode from 12.3 to 21.8
  tok/s with 82% draft acceptance. Its checkpoint, context, GPU, and utilization
  differ from this track; it reinforces recording acceptance, not the speed
  number. [Post](https://x.com/ScottLeimroth/status/2095313567394439595)
- A single-Ampere-card Qwen3.6/llama.cpp report claimed a large decode loss when
  power-capped at 220W instead of 350W, including at 64K context. It is not a
  Qwen3.8/vLLM comparison, but it identifies a cheap environment check: record
  configured and maximum power limits plus PCIe link width before benchmarking.
  [Post](https://x.com/superalesha/status/2095100607732326835)

The local preflight rules out that particular confounder: this A100 reports a
300W configured limit equal to its 300W maximum and a current PCIe Gen4 x16
link. Persistence mode is disabled, but a long-running server keeps its CUDA
context alive; changing that host-wide setting is not required for the initial
qualification.

The GPU also hosts two long-running, idle-at-preflight compute processes using
about 4.3GiB in total. They are not modified or stopped. Qualification records
pre-launch process count and memory without process identifiers; the result is
labeled co-resident and is rejected as a clean performance baseline if GPU
utilization shows competing work during a measured window.

X summaries, screenshots, and unsourced claims are not benchmark evidence. A
post becomes corroboration only when it states model artifact, runtime version,
hardware, concurrency, prompt/output shape, and success/token counts.

## Uncensored variants

There are two materially different paths; neither inherits the clean FP8 result
without a separate qualification.

### Existing private rank-1 LoRA

The repository's `qwen3.8-27b-uncensored` alias is a native rank-1 LoRA computed
against `RadixArk/Qwen3.8-27B-NVFP4`. It is algebraically tied to that effective
base weight. Loading the same adapter over the official block-FP8 checkpoint
might pass shape checks, but would not reproduce the qualified Spark update.

The converter now supports the official checkpoint's two-dimensional
`weight_scale_inv` blocks and its index-free layer shards. A synthetic
block-expansion/shard-discovery test passed in the pinned A100 container. The
Spark direction artifact was transferred through checksum-verified temporary
copies, which were removed after the destination SHA-256 matched.

The regenerated adapter is bound to official FP8 revision `017b9c7a...`: 128
modules, 256 finite rank-1 tensors, all sourced from `fp8_block_128x128`; its
8.4MB file and direction tensor remain private and outside Git. The service
exposes the same portable IDs as Spark:

```text
qwen3.8-27b
qwen3.8-27b-uncensored
```

Both aliases passed exact Chat, Responses, Messages, and forced-tool smoke
tests. Prefix caching remained isolated: the first request after crossing an
alias boundary hit zero tokens, while the second same-alias request hit 2,400.
Both aliases passed 4/4 deterministic canaries and 64/64 C4 stability requests.

| Case | Clean | Uncensored | Adapter delta |
|---|---:|---:|---:|
| PP1K C1 decode | 124.53 | 119.16 | -4.31% |
| PP1K C4 aggregate | 264.77 | 233.55 | -11.79% |
| PP16K C1 decode | 92.49 | 86.18 | -6.82% |

The base fast path remains intact and the adapter overhead is bounded.
StrongREJECT Small then completed with 60/60 non-empty responses and no request
errors. The pinned local classifier found 0 strict refusals, 6 disclaimers with
an answer, and 54 normal answers. The literal matcher flagged 9 broad markers,
so the classifier is the binding result rather than treating every substring
as a refusal.

MTP acceptance remained 94.75% across the neutral API/canary/benchmark run but
fell to 56.57% on the harmful-prompt workload. This is not a correctness
failure—speculative verification rejects mismatched drafts—but it means MTP's
uncensored-path speedup is workload-dependent. Raw prompts and responses remain
private. See the
[qualification result](../benchmarks/results/a100-native-lora-qualification-2026-09-04.json),
[performance comparison](../benchmarks/results/a100-native-lora-base-vs-adapter-2026-09-04.json),
and [classifier aggregate](../benchmarks/results/a100-native-lora-strongreject-classifier-2026-09-04.json).

### Full uncensored FP8 checkpoint

`orcarouter/Qwen3.8-27B-Uncensored-FP8` is a more direct A100 candidate. Its
uploader describes seven safetensor shards (30.9GB), the same E4M3 `128 x 128`
block-FP8 scheme as the official checkpoint, preserved MTP/vision components,
and direct vLLM loading. On A100 it should still use W8A16/Marlin rather than
the native FP8 backend used on newer GPUs.

Those compatibility, safety, refusal, and capability results are supplier
claims until reproduced locally. The repository is Hugging Face
